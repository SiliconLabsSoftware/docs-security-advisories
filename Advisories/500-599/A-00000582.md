## Description

- Several vulnerabilities in the Bluetooth pairing process have been identified in the Bluetooth protocol specification.
- These vulnerabilities are collectively known as Bluetooth LE Re-pairing (BLERP). The report is found here [https://www.ndss-symposium.org/wp-content/uploads/2026-f121-paper.pdf](https://www.ndss-symposium.org/wp-content/uploads/2026-f121-paper.pdf)

- The vulnerabilities are summarized in the following table, for detailed descriptions refer to the paper in the provided link

| Vulnerability # | Description | Impacted product(s) |
| --- | --- | --- |
| 1 | Force a re-pairing with a rogue device by spoofing an already bonded device. | None – re-pairing is not supported by BT122 stack |
| 2 | Re-pairing can use a lower security level than previous (pairing response). | Configuration dependent – application can allow re-pairing and set the minimum key size |
| 3 | Re-pairing with a legitimate device can use a lower security level than previous making brute-forcing the LTK easier. | Configuration dependent – application can allow re-pairing and set the minimum key size | 
| 4 | SMP security request (from peripheral) does not include the maximum encryption key size supported. Using a key with less than the maximum keysize makes brute-forcing the key easier. | None – the product’s Bluetooth stack is not vulnerable to this attack |


### Fix/Workaround

- The mitigation for this vulnerability is to set the minimum LTK keysize to the maximum value (128 bits). See the API guide in the [SDK](https://www.silabs.com/documents/login/software/SiliconLabs_BT122-1.4.0-15.exe) for specific instructions.
