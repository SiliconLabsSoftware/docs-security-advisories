## Description

- DPA countermeasures for ECDH on Curve448 and Curve25519 and EdDSA signing on Curve25519 are unavailable on impacted Series 2 devices due to a lack of hardware support.
    - DPA countermeasures for EdDSA signing on Curve448 are unavailable on impacted Series 2 devices due to a lack of software support.
- A successful DPA attack may allow an attacker to recover confidential data, such as private keys.
    - However, a successful DPA attack requires physical access to a vulnerable device and analysis of many power traces taken during the vulnerable operation to recover confidential data.

- Although both ECDH and EdDSA on Curve25519 and Curve448 are vulnerable, the risk of a successful DPA attack on EdDSA signing is low compared to ECDH because EdDSA incorporates a hash of the private key and input data before signing.

- The following products are known to use vulnerable cryptographic operations:



| Product | Cryptographic Operation Used | Feature Impacted | Details |
| --- | --- | --- | --- |
| Z-Wave SDK | ECDH on Curve25519 | Secure Key Exchange | ECDH on Curve25519 is used by the Z-Wave stack for secure key exchange using ephemeral asymmetric keys when provisioning a new node onto a network. |
| Zigbee SDK | ECDH on Curve25519 | Zigbee Dynamic Link Keys (DLK) | ECDH on Curve25519 is used by the Zigbee stack for generating DLKs using ephemeral asymmetric keys. ECDH on Curve25519 is used by the Sidewalk |
| Sidewalk SDK | ECDH on Curve25519 | Session Key Exchange | stack for secure key exchange using ephemeral asymmetric keys when provisioning a new device to the network. |
| Sidewalk SDK | EdDSA signing on Curve25519 | Authenticated and Encrypted Communication | EdDSA on Curve25519 is used by the Sidewalk stack for encrypting and authenticating communication between Sidewalk devices. |
| Application Layer | ECDH and EdDSA signing on Curve448 and Curve25519 | N/A | Any use of ECDH and EdDSA signing on  Curve448 or Curve25519 in application layer code is vulnerable to DPA attacks. |

### Fix/Workaround

- No fix is available to re-enable DPA countermeasures on Series 2 devices for the vulnerable operations. However, some mitigations may help lower the risks associated with DPA attacks.
- DPA attacks rely on statistical analysis of power traces during vulnerable operations. One mitigation is to roll keys used for these operations frequently.
    - By reducing the number of times the key is used, the number of traces that can be gathered for DPA analysis can be reduced. The best practice is to use each key only once, thereby minimizing the amount of data that can be acquired to extract confidential information.
    - Regular key rotation can help enhance the overall security of a system by reducing the risk for vulnerabilities to be exploited over time. If a key is compromised during an attack, refreshing the compromised key will help prevent further unauthorized access.

- The following mitigation recommendations are listed for each use case:

| Product | Feature Impacted | Mitigation Recommendation |
| --- | --- | --- |
| Z-Wave SDK | Secure Key Exchange | The ephemeral asymmetric key used by the vulnerable operation are unique per node and are used only when provisioning a new node onto a Z-Wave network. No further action is required by a user to mitigate risks. |
| Zigbee SDK | Zigbee Dynamic Link Keys (DLK) | The ephemeral asymmetric keys used by the vulnerable operation are used only once when deriving the DLKs. No further action is required by a user to mitigate risks. |
| Sidewalk SDK | Session Key Exchange | The ephemeral asymmetric keys used by the vulnerable operation are used only once when deriving the session keys for secure key exchange. No further action is required by a user to mitigate risks. |
| Sidewalk SDK | Authenticated and Encrypted Communication | Best practice is to roll keys used by the vulnerable operation frequently, or after each use. If key rolling cannot be implemented, no further actions are available to mitigate risks. |
| Application Layer | N/A | Keys used by the vulnerable operation can be refreshed based on the user-defined lifetime of the key. Silicon Labs recommends users to refresh these keys after each use, using the following APIs: psa_destroy_key(), psa_generate_key() |
