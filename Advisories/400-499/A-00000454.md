# Silicon Labs Security Advisory A-00000454 : Zigbee Incoming Network Frame Counter does not prevent replay attacks

Flags: Zigbee

CVSS Severity: Medium

### Source Product Impact Details

- Silicon Labs EFR32x and EFM35x SoCs and Modules running the EmberZNet Zigbee stack...
    - NOT utilizing Application Support Sublayer (APS) security
- Note that Zigbee broadcast devices remain vulnerable as broadcast occurs below the APS layer

## Description

- A defect exists in the Zigbee protocol’s network layer potentially allowing replay attacks. In order to detect duplicate frames, the Zigbee protocol specifies that Outgoing and Incoming Network Frame Counters be maintained, however ONLY the Outgoing Frame Counter is mandated to be persistent.
- In certain circumstances (such as loss of power) a device’s record of its neighbors Incoming Frame Counters may be lost, enabling a malicious user to replay previously observed packets without knowing the network key.
- As a result, the Network Frame Counter specified in the Zigbee protocol is not sufficient to prevent replay attacks against the network layer.

### Fix/Workaround

- APS Layer Security link key management provides additional protection against replay attacks. For any applications that require replay attack hardening, APS Layer Security as described in [AN1233 – Zigbee Security section 2.4](https://www.silabs.com/documents/public/application-notes/an1233-zigbee-security.pdf) should be enabled.
    - Enabling APS enables APS Layer Security for all Unicast devices. However broadcasts are not replay-protected by APS Layer Security.
    - Contact [Silicon Labs Techincal Support](https://www.silabs.com/support) for more information on enabling APS in your application.
    - Despite the hardening provided by APS Security, a known vulnerability exists in APS for Zigbee r22 and earlier involving neighbor table loss on power reset. This vulnerability will be addressed in a future revision of the Zigbee protocol.
