# Silicon Labs Security Advisory A-00000384 : Informational: NCPs and RCPs with Communication Bootloaders Require the Host to Authenticate Secure Upgrades

Flags: MCU

CVSS Severity: -

CVSS String: -

## Product Impact

| Product | Impacted Version | Main SDK | Impacted Version | CVE |
| --- | --- | --- | --- | --- |
| - | - | - | - | - |

### Source Product Impact Details

- EFR32 and EFM32 SoCs and modules using Communication Bootloaders are affected

- EFR32 and EFM32 SoCs and modules using Storage Bootloaders are not affected

## Description

- Devices using Communication Bootloaders don’t have access to local storage, so the GBL file cannot be authenticated before it is acted upon. This means that when a signed GBL upgrade image is sent to the NCP or RCP, its upgrade payload is immediately applied to the target flash address, thereby overwriting the application before its authenticity can be verified.

- More information on Gecko Bootloader can be found in [UG489](https://www.silabs.com/documents/public/user-guides/ug489-gecko-bootloader-user-guide-gsdk-4.pdf) (for GSDK 4.0 or later) and [UG266](https://www.silabs.com/documents/public/user-guides/ug266-gecko-bootloader-user-guide.pdf) (for earlier versions of GSDK).

### Fix/Workaround

- The host processor should verify the authenticity of signed upgrade images before sending them to the NCP or RCP. Instructions below.

- Secure Boot should be enabled to guarantee authenticity of the firmware.

### GBL Signature Verification:

- For the host processor to verify the authenticity of a signed upgrade image, it needs to do the following: 

    1. Extract the signed portion of the data from the GBL.
    2. Extract the signature from the GBL.
    3. (Optional) Convert the GBL signature to the DER format.
    4. Verify the signature using the public sign key and the signed portion of the GBL.

- To perform step 1, you should remove the last 84 bytes of the file. The last 84 bytes contain the signature tag itself and the end tag. This can be done in Linux with the following command:

        cp sample-signed.gbl extracted-image.txt && truncate -s-84 extracted-image.txt

- To perform step 2, you should extract the 64 bytes after the 76th byte from the end. This is where the signature itself is stored. This can be done in Linux with the following command:

        tail -c76 sample-signed.gbl | head -c64 > signature.txt

- Depending on how you implement step 4, you may first need to convert signature.txt into the DER format. A description of DER signature formatting is given [here](https://bitcoin.stackexchange.com/questions/92680/what-are-the-der-signature-and-sec-format). Because the conversion depends on the most significant bit of both R and S, a simple one-line implementation is not possible. For help implementing this conversion, contact us at [https://www.silabs.com/support](https://www.silabs.com/support).

- To perform step 4, you should use a cryptography tool such as openssl to verify the extracted image against the signature and public key (which should be made available on the host device ahead of time). If the signature was converted to the DER format, this can be done in Linux with the following command: 

        openssl dgst -sha256 -verify sign_pubkey.pem -signature signature.der extracted-image.txt
