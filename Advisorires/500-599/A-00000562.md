## Description

- Eight security weaknesses in the Bluetooth Mesh Specification were identified and reported by security researchers. For more information on each of these weaknesses, refer to the researcher’s paper, referenced in the Attribution section below. Note: at the time of publication of this advisory, the paper below is not yet publicly available.
- The summary of each of the weaknesses identified is listed below:
    1. Downgrading to unauthenticated provisioning via a MiTM attack
    2. Certificate-based provisioning does not require authentication of provisioner
    3. Short passkeys or reused passkeys are allowed by the BT Mesh specification
    4. AES-CMAC collision resistance could lead to impersonation attacks
    5. Identities in Bluetooth Mesh specification lack clarity and uniqueness
    6. Lack of insider security can introduce weaknesses in the network
    7. Lack of clarity on procedure to become a configuration manager can lead to privilege escalation
    8. Compromise of the configuration manager can enable key injection attacks during refresh procedures

### Fix/Workaround

- The 8 weaknesses described in the researcher’s paper were each addressed using one of the three methods:
    - Editorial clarifications in the Bluetooth Mesh Protocol 1.1.1 that clarify the specification’s intentions
    - Updates to [Bluetooth Mesh Security Overview](https://www.bluetooth.com/bluetooth-resources/mesh-security-overview/) documentation
    - Corresponding updates to [Silicon Labs’ Bluetooth Mesh Best Practices](https://docs.silabs.com/btmesh/latest/btmesh-provisioning-security-best-practices/) Documentation
- A summary of the weaknesses and how they were addressed are listed in the table below:


| Weakness | Description | How it is Addressed | Link to Additional Details |
| --- | --- | --- | --- |
| 1 | Downgrading to unauthenticated provisioning via a MiTM attack | Updated Silicon Labs’ Bluetooth Mesh Documentation for clarity on provisioner’s abilities to reject lower security devices | [BT Mesh Best Practices - Capability Negotiation](https://docs.silabs.com/btmesh/latest/btmesh-provisioning-security-best-practices/#capability-negotiation) |
| 2 | Certificate-based provisioning does not require authentication of provisioner | Updated Silicon Labs’ Bluetooth Mesh Documentation for clarification that a rovisionee can request authentication data from a provisioner  | [BT Mesh Best Practices - Capability Negotiation](https://docs.silabs.com/btmesh/latest/btmesh-provisioning-security-best-practices/#capability-negotiation) |
| 3 | Short passkeys or reused passkeys are allowed by the BT Mesh specification | Updated Silicon Labs’ Bluetooth Mesh Documentation for prohibiting reuse of passkeys | [BT Mesh Best Practices - Device Authentication](https://docs.silabs.com/btmesh/latest/btmesh-provisioning-security-best-practices/#device-authentication) |
| 4 | AES-CMAC collision resistance could lead to impersonation attacks | Addressed by an update to the Bluetooth Mesh Spec in 1.1 | N/A |
| 5 | Identities in Bluetooth Mesh specification lack clarity and uniqueness | Updated Silicon Labs’ Bluetooth Mesh Documentation for clarity on PKI recommendations | [BT Mesh Best Practices – Consider PKI Integrity](https://docs.silabs.com/btmesh/latest/btmesh-provisioning-security-best-practices/#consider-pki-integrity) |
| 6 | Lack of insider security can introduce weaknesses in the network | No actions taken. The prerequisites for an attack under these circumstances require multiple secret device and network keys to be exposed. Best practices for key management are recommended to address this weakness. | N/A |
| 7 | Lack of clarity on procedure to become a configuration manager can lead to privilege escalation | End device manufacturers are responsible for design of procedure for a device to become a configuration manager. Series 2 and Series 3 Silicon Labs devices may offer security features on MCUs that can be used to protect against certain attacks. | N/A |
| 8 | Compromise of the configuration manager can enable key injection attacks during refresh procedures | End device manufacturers are responsible for design of procedure for a device to become a configuration manager. Series 2 and Series 3 Silicon Labs devices may offer security features on MCUs that can be used to protect against certain attacks. | N/A |
